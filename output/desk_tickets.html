3 · What would have been simpler as one agent

Most of this board, honestly. Campus Customs is 9 tables plus 2 support tables and a few dozen rows, and all 23 MCP tools fit in one context. The token bill makes the case: the first pass of all three tickets cost 130,135 tokens, and the whole session including the decision and follow-ups cost 257,256. The expanded prompts made behavior better but each call heavier: about 23% more tokens than the one-line run's 105,671 for the first pass, because every hand-off re-sends a long prompt. get_ticket_details ran 21 times across the six runs, because every agent re-reads the same ticket.

  • 102 is a 3-call job for one agent: get_lease(1) → request_payment_approval("rent", 1) → update_ticket_status. We used 11 model calls and three agent loops.
  • The stale-draft bug is a hand-off problem. Facts went stale in the gap between agents. The Boss passed along "reorder draft #3 is blocked" from an old note, and Customer Service repeated it. One agent that re-calls check_vendor_can_ship before writing would never have relayed a secondhand fact.
  • 103's discount math is one call: quote_bulk_price returns price, margin, stock and shortfall together.

What the multi-agent design really buys is separation of duties: only Accounting can request money, like a store manager in a retail chain who can't cut a check. But that control is enforced in code (per-role tool filtering, plus a human-only approve_and_pay that refuses agent approvers), not by having separate LLMs. My recommendation for a shop this size is one agent with role-scoped tool sets per ticket type, saving the multi-agent overhead for volume, like a back-to-school rush with hundreds of tickets.

5 · Three new problems this team can't solve, and what I'd build
  1. The $160 cash crunch: October rent and no revenue. The Cash tab ends at $160.00, with $2,400 rent due 2026-10-02 and a released hoodie reorder that would bill about $264. What I'd change next

The prompt rewrite already did its job: no duplicate hand-offs, a customer reply on every ticket, and exact-quantity reorders. Next I'd make the system event-driven: when approve_and_pay clears an invoice, automatically queue a follow-up for every ticket blocked on that vendor, instead of waiting for me to click Run. Then I'd make Accounting check cash against future bills from released reorders, and trim the prompts (or cache them) to win back the ~23% token increase. At scale, that difference is real money, and the customer gets accurate news faster.
